# Minimalist OS comparison — Phase 9.5 research, not implementation

## Scope and evidence rules

This audit compares the existing Rosti Phase 9 architecture with official MenuetOS documentation and nanochess bootOS source. It does not start Phase 10, implement an application loader or GUI, change the production target, or authorize deployment. The live research branch was `maintenance/phase9-5`, HEAD `9da1d48`; older handover references to `main` describe the checkpoint, not this working branch.

**Source fact** means observed source behavior. **Documented claim** means the vendor says it; no independent execution was performed. **Hypothesis/proposal** means an independently reasoned Rosti option, not an implemented feature. No bootOS/Menuet build, benchmark, emulator run, binary disassembly or restricted-source inspection was performed. The Menuet claim that assembly outperforms every other language is **unverified**, not a conclusion of this audit. Artifact size, runtime residency, throughput, latency and correctness are distinct measurements.

## bootOS source hazards that must not be ported

1. `filename_length` scans to NUL without a maximum. `save_file .empty` uses that count with `rep movsb`, so a name exceeding the 16-byte entry can overwrite following entries or memory. README's nominal constraints do not implement validation.
2. `input_line` writes indefinitely; repeated backspace before the buffer start decrements DI outside it. `enter_command` similarly advances its output pointer beyond the program sector without a bound. These are source-derived hazards, not exploit demonstrations.
3. `save_file` invokes delete first, copies/publishes the new directory name, then writes the data sector. Failure/interruption can destroy old naming/content correspondence. No COW, commit root or ordered flush contract exists.
4. `disk` retries BIOS carry failures without a retry budget. A bad/absent floppy can trap control indefinitely. The advertised service carry statuses do not make disk failures bounded.
5. Executed code shares the OS memory, IVT, stack/hardware privileges. Compact interrupt services provide convenience, not a trust boundary.
6. README load/save pointer wording is reversed relative to executable code: `load_file` restores destination as ES:BX for BIOS read; `save_file` restores source for BIOS write. Use code when documenting direction; do not transplant contradictory comments.

## Benefits, risks and ranked recommendations

Benefit/risk are qualitative engineering judgments, not benchmark scores. Rank orders investment for the current mission, with prerequisites explicit.

| Rank | Recommended action | Benefit | Risk/cost | Decision and acceptance condition |
|---|---|---|---|---|
| 1 | Keep current safe boot, descriptors, FS v1 and IRQ ownership; document all added bounds | High correctness/recovery value | Low change cost | Adopt as invariant; no safety-layer deletion to hit an image-size target |
| 2 | Establish release-size/residency/stack/I/O latency evidence before optimization | High ability to target real constraints | Low–medium tooling effort | Future work: distinguish debug ELF sections, stripped loadable bytes, ISO overhead, static residency and workload peak; preserve acceptance |
| 3 | Bounded, versioned, independent ELF32 application ABI [design](ROSTI_APPLICATION_ABI_DESIGN.md) | High path to small reusable tools | High privileged-boundary/security cost | Design now; implementation separately authorized only after user pages, TSS, traps and cleanup can be verified |
| 4 | Event-based waiting and bounded request/event buffers | High idle efficiency and explicit ownership | Medium; queue loss and scheduling interaction | Adopt pattern, not Menuet numbers/code; never claim cooperative code is malicious-code isolation |
| 5 | Optional opaque software GUI [design](ROSTI_LIGHTWEIGHT_GUI_DESIGN.md) | Medium usability without GPU lock-in | Medium–high framebuffer/input/memory cost | Text-first; no GUI prerequisite for recovery, filesystem or ABI |
| 6 | Profile then optimize localized hardware/data movement | Medium potential throughput | Medium cache/assembly risk | Hypothesis: batched bounded copies/dirty regions help; measured before/after, no arbitrary MTRR copying |
| 7 | Custom flat app format or foreign compatibility layer | Low immediate benefit | High ABI/tool/security/licensing maintenance | Defer; ELF32 initial scope excludes Linux/POSIX/Menuet/boot-sector binary compatibility |
| 8 | Rewrite Rust in assembly, replace GRUB, replace RostiFS with sector files, copy high-frequency scheduler/transparency | Unproven or negative mission benefit | Very high regression/security cost | Reject for Phase 9.5; 512-byte minimalism is a different objective, not a modernization blueprint |

**Independent hypotheses:** small syscall surfaces, explicit bounded buffers and event waiting can reduce complexity/idle CPU use; software opaque rendering can work without a GPU stack. Neither hypothesis establishes that fewer layers or assembly inherently yield a faster, safer OS. Existing layers encode authority, stale-handle checks and durable ordering; remove accidental duplication only, not these contracts.

## License and next-step boundary

Menuet32 and Menuet64 are not interchangeable licensing cases. The GPL v2 page alone does not establish every distributed file's exact grant or an `or-later` designation. Review per-file notices before any proposed GPL reuse, preserve obligations, and obtain legal review for combined distribution. Menuet64 source availability for selected applications/drivers does not override its restrictions; assets have their own licenses. No restricted material was reverse-engineered and no upstream code/assets were imported. bootOS BSD-2-Clause permits reuse with notices, but permission does not make its unsafe contracts suitable.

This delegated research contributes design documentation only; that restriction describes these three documents and this subtask, **not the entire Phase 9.5 maintenance milestone**. The parent audit has recorded a baseline/read-only inventory and may carry out user-authorized small measured maintenance, including a cat-path optimization. No fresh build, boot, performance test or physical durability result is claimed by this research subtask. Application/GUI implementation remains outside these design documents; eventual feature work must retain existing release gates and add boundary/GUI tests. Phase 10's initramfs/verified-image/recovery work remains unstarted by this document.
